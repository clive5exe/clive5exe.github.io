Thryve: Connecting class bookings to instructor pay

Nobody showed up to class. Does the instructor still get paid? At the pilot studio, yes, as long as the studio hadn’t canceled it. Now try to find that class in a query that starts from the bookings table.

That was the job on Thryve: take software that already had a schedule, checkout and dashboards, and find out whether those pieces told the same story once a real studio was using them. I was the solo developer at Daytona Lab, which in 2026 means one person and a small crowd of AI coding agents that are very confident and occasionally right. I inherited a substantial codebase and took it through launch on the web and iPhone. The part I’m proudest of is what happens between someone tapping Book and an instructor seeing the right number on a pay statement, mostly because of how many ways that chain turned out to be quietly broken.

One recurring class, many actual Tuesdays

A studio owner offers reformer Pilates every Tuesday at 7. That’s a series. The Tuesday that runs next week is an occurrence, and the occurrence is what people book. It has its own seat limit and its own instructor. Someone cancels, a waitlisted member takes the seat, a substitute teaches that week. None of that should rewrite every other Tuesday on the calendar.

The data model got there in layers. The original classes table holds one row per scheduled occurrence with absolute start and end times; it was never a recurrence rule. A later class_sessions table became the operational layer: lifecycle status, a snapshot of the policies in force, and the thing rosters, waitlists and reconciliation actually point at. Series live in their own table with skip dates and studio blackout dates, and a generator turns them into sessions four weeks ahead, converting local time to UTC with Luxon so the 7pm class is still at 7pm after daylight saving changes.

Two details from that work still make me smile. First, when I measured it in September, the series generator had never run. Anywhere. A migration comment records the count of generation runs at the time: zero. Second, rather than teach every booking, capacity and money path about the new sessions table, a trigger creates a matching classes row for every series occurrence. The comment on it is “mirror, don’t teach every reader,” which is the most pragmatic sentence I wrote all year. The cost of having two tables showed up immediately: 1,084 of the 1,093 most recent bookings had no session id at all, and the fix assigns it under the class row’s lock so two simultaneous bookings can’t create two sessions for the same class.

Substitutes and waitlists both live on the occurrence. Swapping the instructor stamps the session with the time of the substitution, which opens a grace window for members to cancel without the usual late-cancel penalty. The pay engine pays whoever is on the session, so the substitute gets paid, not the regular. The waitlist doesn’t silently push someone into a seat; it makes an offer, under a per-class advisory lock taken before the row lock, and the member claims it through the normal paid checkout. An earlier version let members forge their own offers through the auto-generated REST API, which is a fun thing to find in a fitness app.

Who holds the money

Members pay the studio, not Thryve. Every booking is a direct charge on the studio’s own connected Stripe account, with a 5% application fee for the platform taken out of the studio’s proceeds. The studio’s plan sets the fee, and the free plan used to be 7.5% until every plan moved to 5%. If Thryve disappeared, the money would already be sitting in the studio’s account.

People can book without an account. On the web that’s a Stripe Checkout Session on the studio’s account, and the important rule is that the browser coming back from Stripe proves nothing. Only the checkout.session.completed webhook finalizes the booking. It checks that Thryve’s own record of that session exists for that account, amount and currency, then books the seat through a single atomic database function with an idempotency key derived from the session id. If the class filled up while the guest was typing their card number, it refunds in full under a fixed key so a retried webhook can’t refund twice. Guest checkout is also rate limited per IP and per class, because an anonymous form that charges cards is exactly what card testers look for.

The webhook taught me the most expensive lesson in the project. A charge.succeeded handler was throwing on a database column that existed in staging but not in production, and the handler still answered Stripe with a 200 every time. The commit that fixed it says the webhook was “losing revenue on every transaction.” Nothing alerted, because from Stripe’s side every delivery succeeded. Now every event goes through a ledger table first, so a duplicate delivery is dropped before it touches a booking, and a failure is a failure.

Verified, but not activated

Turning on live payments was its own small mystery. Thryve’s Stripe account was fully verified, identity and business and all, and still every studio that tried to connect got “Your account must be activated.” The missing piece wasn’t on the account at all: Stripe Connect needs a separate platform profile, and passing identity verification doesn’t fill it in. Once that profile was filled in, studios could connect. There’s no code change to show for it, just a reminder that “verified” and “allowed to do the thing” are two different booleans.

Six digits at the front desk

Every booking gets a 6-digit check-in code. The member shows it, and the studio or instructor types it in or taps the member’s name on the roster; both go through the same engine. Six digits sounds trivial until you ask two questions: how random is it, and can two people at the same studio have the same code at the same time? The codes come from a cryptographic random source with rejection sampling, so the leading digits aren’t biased by a modulo. Uniqueness is enforced by an exclusion constraint over a time range, so a studio never has two live codes that match, while the same six digits can be reused next month.

Checking in writes a check-in row and moves the booking to attended. If two staff members scan the same code at the same moment, the database’s unique constraint picks a winner and the other one hears “already checked in.” Walk-ins get a QR poster at the front desk: a drop-in scans it, sees the classes starting soon, pays, and is checked in without making an account.

The class that never finished

Here’s the bug I’d want another engineer to hear about. A class moves through a lifecycle on its own: bookable, check-in open, roster locked, in progress, pending reconciliation, reconciled. Three scheduled jobs, staggered every 15 minutes, push it along: one advances sessions, one reconciles them, one accrues payroll. No pay line is ever written until a session is stored as reconciled.

The jobs didn’t run, and the history of why is a little comedy in four acts. The commit that first touched them says it plainly: “these crons have never actually run anywhere,” because the host the app ran on didn’t execute vercel.json at all. On Vercel’s hobby tier, schedules more frequent than daily were rejected, so the advancer went from every five minutes to once a day, which with one step per run meant a class took about four days to reach reconciliation. Then Vercel Cron sends GET, and fourteen routes only accepted POST, so every scheduled run got a 405 and logged nothing interesting.

The reason nobody noticed is my favourite part. Check-in needed to know whether a class was open, so a fix in September made the app work the status out from the clock at read time, because “a session materialised as ‘bookable’ stays ‘bookable’ forever.” That was correct, and it kept check-in working perfectly, which hid the fact that the stored status, the one payroll reads, never moved. The front desk was happy; the pay statements were empty.

When I fixed the GET problem I left the money chain off on purpose. Turning it on would have sent 135 long-past bookable sessions straight into automatic attendance, no-show fees, credit consumption and pay lines, old sessions generating fees and pay nobody owed. So the re-enable came with a cut-off date: only sessions after it are processed. The cut-off can be moved later by configuration but never earlier, so reopening the backlog takes a code change and a review, and if the job can’t read the cut-off it refuses to run rather than guessing. It now runs every 15 minutes in batches of 100 with a 40-second time budget, walks each session through every step that’s due in one go, and every money step claims its row with a conditional update first so a retry can’t credit anything twice.

Paying for an empty class

Back to the opening question. The pilot studio decided that a class the studio doesn’t cancel gets paid, even if nobody shows up. That sounds like a settings toggle and was actually a rewrite. Pay had been counted from bookings, and an empty class has none, so it simply didn’t exist as far as payroll was concerned. The engine now counts classes actually taught: canceled sessions earn nothing, and an empty class is paid unless the studio explicitly turns that off. The setting originally defaulted the other way; flipping it was a deliberate product decision, not a fix.

The second half of that change was making the estimate tell the truth. The Hours view an instructor sees was computed separately from the real pay engine, and it said “No hours in this period” for a class that had been taught to an empty room. Two pieces of code answering the same question will eventually answer it differently, so now the estimate follows exactly the same rules as the engine.

Two sources of truth

One instructor’s rate was $30 per class in the agreement they had accepted and $30 hourly in the studio’s settings. The cause was a small copy bug: every piece of code that mirrored an agreement into settings mapped anything that wasn’t a percentage to hourly, so a flat per-class rate quietly became an hourly one. For a 50-minute class the difference is small, which is exactly why nobody caught it.

The fix wasn’t to fix the mirror; it was to stop having two answers. The accepted compensation agreement is now the only rate source. The engine picks the highest accepted version in effect on the date of the class, and if there isn’t one, it writes no pay line. There used to be a $50-an-hour fallback for that case, and it’s gone: pay is never guessed. Offering an instructor a new version keeps the accepted one in force until they accept the new one, so a studio can’t change someone’s rate retroactively by sending a draft. The pay models are deliberately few: flat per class, hourly on scheduled minutes, or a percentage of list price times attendees.

Pay lines you can’t edit

Each reconciled session produces one pay line per instructor, and that line snapshots everything that produced the number: the agreement id and version, the rate, the minutes, the attendee count and the base. Pay is never recalculated later. A unique index on instructor and session makes a replayed job harmless, and the engine treats the unique violation as “already accrued.”

The database enforces the rest. A trigger compares the new row to the old one with the statement id removed, and refuses the update if anything else changed. Once the statement a line belongs to is approved or paid, even attaching it elsewhere is refused. Statements go draft, approved, paid, or void, through database functions only the service role can call, under a per-studio advisory lock. I like this design because it doesn’t depend on anyone, human or agent, remembering not to edit money.

Two money flows, and the one I turned off

There are two flows of money in a studio, and for a while the code had three. Members pay the studio: that’s the direct charge above. The studio pays its instructors: that happens outside Thryve, and Thryve keeps the books, recording the method, date and reference when a statement is marked paid. The third flow was an automated payout that transferred instructor pay from Thryve’s own platform balance to each instructor’s connected account, while the class money had landed with the studio. In other words, the platform was paying the studio’s staff with its own money. I killed it in October with a kill switch that blocks by default.

The old payout engine is still in the code behind that switch, and it has one idea worth keeping. Stripe idempotency keys expire after 24 hours, so a payroll retry the next day with the same key is a brand-new transfer. The engine claims each payout row in the database first and treats Stripe’s key only as a backup. If an instructor hasn’t finished onboarding, it releases the claim and records the failure so a later retry can succeed.

The iPhone app

The native app is SwiftUI on iOS 17 and up, and it covers all three roles: members book and pay, instructors see their schedule, rosters and earnings, and studio owners run check-in, payroll and analytics with Swift Charts. It talks to a dedicated mobile API through a Swift actor that sends the Supabase session token as a Bearer token. On the server that API uses the service role and scopes every query to the caller itself.

Apple Pay goes through Stripe’s native payment sheet, push notifications come over APNs and open the right message thread when tapped, and booking confirmations offer to add the class to the calendar. The work I enjoyed most was unglamorous: studio tab taps took about six seconds and now take between zero and 1.4. Native guest checkout is built on the phone and waiting on its backend routes; until those ship, the app says guest booking isn’t available yet instead of failing strangely.

What I’d tell the next developer

If a status can be computed from the clock, make sure something still stores it, or you’ll have a front desk that works and a payroll that doesn’t. If two pieces of code answer the same question, delete one. If a webhook returns 200, check that it did the work. And never trust a 24-hour idempotency key with money. Some things are still open: native guest checkout is waiting on the server, the refund-fee credit job sits behind a kill switch that defaults to off, and most of this was proven on one pilot studio, not a hundred. But the instructor who taught an empty room gets paid now, and the number on the statement came from the agreement they actually accepted.
